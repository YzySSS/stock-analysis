# 股票分析系统改进计划 - 完整版

## 2026-06-12 架构更新：纪律型私人投研工作台

> 本节为当前最新产品与架构边界，优先级高于早期“14 周完整平台化”设想。
> 当前项目不走自动交易系统，也不急于拆微服务；先建设“能约束交易纪律、能解释、能复盘”的个人投研工作台。

### 1. 最新产品定位

当前阶段定位为：

```text
个人纪律型投研工作台
```

核心目标：

- 现阶段只给个人使用，后续可能开源给其他人自部署。
- 产品形态是私人投研工具，不是券商交易终端，也不是自动交易机器人。
- 输出用于辅助分析，重点帮助使用者遵守交易纪律、减少个人情绪影响。
- 系统不自动下单，不接券商自动交易；边界停留在“建议、提醒、复盘、纪律约束”。
- 后续开源时仍沿用当前模型和数据源体系，但使用者必须配置自己的 API key / 数据源 key。

### 2. 推荐架构风格

采用：

```text
模块化单体 + 异步任务驱动 + 可追溯 AI 决策层
```

暂不拆微服务。

原因：

- 当前主要是个人使用，部署和排障简单性优先。
- 后续开源时，模块化单体更容易安装、理解和二次开发。
- 页面响应速度、数据准确性、建议可解释性优先于服务拆分。
- DeepSeek / AI 分析允许后台异步执行，不应阻塞核心页面加载。
- AI 可以作为决策者，但必须被真实行情、技术指标、筹码、资金流、持仓策略和纪律规则约束。

### 3. 核心领域边界

#### 3.1 数据层：回答“事实是什么”

负责采集、同步和质量标记：

- 行情 K 线
- 盘中接近实时价格
- ETF 行情 fallback
- 资金流
- 筹码分布
- 舆情与新闻质量
- 基本面 / 估值

要求：

- 行情 K 线是当前最可信数据主线。
- 数据缺失时必须显式暴露 `data_insufficient` 或缺失原因。
- 不允许在关键数据缺失时硬编买卖建议。

#### 3.2 指标层：回答“结构是什么”

负责从数据层计算结构化指标：

- MA5 / MA10 / MA20 / MA60
- ATR / 波动率
- 20 日高低点
- 动态支撑位 / 压力位
- 量能确认
- 筹码胜率、筹码中枢、上方压力区
- 资金活跃度与资金方向

要求：

- 支撑位、压力位、止损位、止盈位优先由系统按规则计算。
- AI 可以解释这些位置，但不能脱离数据凭空改数值。

#### 3.3 纪律层：回答“应该遵守什么规则”

持仓策略固定为三类：

| 策略 | 默认持仓周期 | 默认风控倾向 | 重点指标 |
| --- | --- | --- | --- |
| 短期 | 1-5 天 | 最大可接受亏损 3%-5% | 实时价、MA5、MA10、量能、ATR |
| 波段 | 1-4 周 | 最大可接受亏损 6%-10% | MA20、箱体、筹码压力、资金活跃 |
| 长期 | 1-6 个月以上 | 最大可接受亏损 12%-18% | 大级别趋势、估值、基本面、行业逻辑 |

当前约定：

- 最大可接受亏损按策略默认设置。
- 后续可支持单只持仓覆盖，但 V1 先不强迫用户逐票配置。
- 同一持仓的 AI 建议在一定时间内复用，不每次页面加载都重复生成。
- 违反纪律时必须提醒，例如跌破止损、亏损超限、持仓周期超限、追高风险等。

#### 3.4 AI 决策层：回答“综合判断是什么”

AI 可以作为最终建议生成者，但必须基于结构化输入快照。

每次 AI 建议必须保存：

- `position_id`
- `stock_code`
- `strategy_type`
- `holding_cost`
- `quantity`
- `realtime_price`
- `latest_trade_date`
- `technical_indicators`
- `support_levels`
- `resistance_levels`
- `chip_snapshot`
- `moneyflow_snapshot`
- `sentiment_snapshot`
- `discipline_rules`
- `model_name`
- `prompt_version`
- `raw_response`
- `parsed_decision`
- `decision_level`
- `created_at`
- `expires_at`

建议分级：

| 等级 | 含义 |
| --- | --- |
| `critical_exit` | 强制止损 / 严重违反纪律 |
| `reduce` | 减仓 |
| `hold_watch` | 持有观察 |
| `add_allowed` | 允许加仓 |
| `no_action` | 不操作 |
| `data_insufficient` | 数据不足，不给建议 |

#### 3.5 复盘层：回答“建议有没有用、纪律有没有执行”

后续需要记录：

- AI 建议后的真实走势
- 建议是否触发止损 / 止盈 / 加仓
- 使用者是否违反纪律
- AI 建议与系统硬规则是否冲突
- 不同策略周期下的实际表现

目标不是让 AI “永远预测正确”，而是让系统逐步评估：

- 哪类建议可靠
- 哪类数据缺失会误导
- 哪类纪律最能降低情绪化交易

### 6. 当前架构落地状态

截至 2026-06-12，持仓建议链路已经从“页面同步问 AI”改成“后台生成、落库复用、页面读取”的形态：

- `portfolio_position` 记录手动持仓、成本、数量、持仓策略、买入时间和风控覆盖项。
- `portfolio_advice_run` 记录每次 AI 建议的状态、输入快照、模型、prompt 版本、原始输出、解析结果、建议等级和过期时间。
- `/api/portfolio` 只读取持仓事实、本地纪律摘要和最近未过期 AI 建议，不再等待 DeepSeek。
- `POST /api/portfolio/{position_id}/advice/refresh` 触发后台刷新建议。
- 页面进入时先看摘要；完整建议通过详情弹窗查看。
- 数据不足、AI 失败、纪律冲突不会阻塞持仓列表加载，而是作为状态暴露给页面。

当前架构的主线已经切换为：

```text
持仓事实
  -> 数据快照
  -> 系统指标与纪律规则
  -> AI 建议生成
  -> 建议落库
  -> 页面复用
  -> 后续复盘评价
```

### 7. 最新模块边界

#### 7.1 持仓模块

职责：

- 管理手动录入持仓。
- 按单个持仓选择短期、波段、长期策略。
- 计算成本、现价、浮盈亏、持仓天数、策略约束和本地纪律提醒。
- 读取最近一次有效 AI 建议，不主动发起慢请求。

不负责：

- 自动下单。
- 账户资金同步。
- 券商接口接入。
- 替用户决定真实交易。

#### 7.2 AI 建议模块

职责：

- 基于结构化输入快照生成建议。
- 输出建议等级、摘要、完整分析、风险、操作计划、支撑压力和失效条件。
- 保存原始响应与解析结果，方便后续排错和复盘。
- 在模型失败或输出不可解析时明确失败原因。

约束：

- AI 不直接改写系统计算出的成本、现价、止损、压力位等硬数据。
- AI 建议必须带 `prompt_version` 和 `model_name`。
- AI 建议必须有过期时间。
- AI 建议要能被本地纪律规则覆盖或否决。

#### 7.3 纪律规则模块

职责：

- 根据持仓策略定义最大亏损、持仓周期、追高风险和止损约束。
- 在 AI 建议之前先给出本地硬规则判断。
- 在 AI 建议之后检查是否存在冲突。
- 生成可用于页面展示的 `discipline_alerts`。

当前规则优先级：

1. 数据不足时，不给确定性操作建议。
2. 跌破止损或亏损超限时，本地纪律优先级高于 AI 观望建议。
3. 已明显追高时，不允许 AI 直接给出无约束加仓建议。
4. 短期策略对盘中价格更敏感，长期策略对日内波动降噪。

#### 7.4 复盘评价模块

职责：

- 统计 AI 建议发出后的真实走势。
- 判断建议是否命中、失效或反向。
- 区分“建议质量”和“纪律执行”。
- 形成长期可查询的建议历史。

这是下一阶段的主建设方向。

### 8. P3 复盘闭环设计

P3 的目标不是继续让 AI 写更多文字，而是回答：

```text
这条建议后来有没有用？
我有没有遵守纪律？
系统哪里判断错了？
```

#### 8.1 新增建议结果评价表

建议新增：

```text
portfolio_advice_outcome
```

核心字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `advice_run_id` | 对应 `portfolio_advice_run.id` |
| `position_id` | 对应持仓 |
| `code` | 股票代码 |
| `decision_level` | 建议等级快照 |
| `base_price` | 建议生成时参考价格 |
| `evaluate_at` | 评价时间 |
| `horizon_days` | 评价周期，支持 1 / 3 / 5 / 20 |
| `latest_price` | 评价时最新价 |
| `return_pct` | 从建议价格到评价价格的收益 |
| `max_gain_pct` | 建议后最大浮盈 |
| `max_drawdown_pct` | 建议后最大回撤 |
| `stop_loss_touched` | 是否触发止损 |
| `take_profit_touched` | 是否触发止盈 |
| `support_broken` | 是否跌破关键支撑 |
| `resistance_broken` | 是否突破压力 |
| `outcome_label` | `hit` / `miss` / `neutral` / `invalidated` / `data_insufficient` |
| `quality_score` | 建议质量分 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

#### 8.2 评价口径

不同建议等级使用不同评价标准：

| 建议等级 | 正向命中 | 负向失败 |
| --- | --- | --- |
| `critical_exit` | 后续继续下跌、跌破支撑、触发止损 | 后续快速反弹且未跌破纪律线 |
| `reduce` | 后续风险扩大或收益回吐 | 后续继续强势突破 |
| `hold_watch` | 未触发止损，走势符合区间判断 | 跌破止损或出现明显反向 |
| `add_allowed` | 后续上涨或突破压力 | 加仓后快速回撤 |
| `no_action` | 波动不大，未出现明确信号 | 出现本应识别的风险或机会 |
| `data_insufficient` | 后续仍缺数据，不计入质量 | 数据其实足够但系统误判不足 |

注意：

- `data_insufficient` 不应强行算成 AI 预测失败。
- 如果建议生成时关键数据缺失，评价时必须保留缺失原因。
- 同一周期内同时触发止盈和止损时，短期策略按保守口径优先判定风险；长期策略需要结合收盘价与支撑位确认。

#### 8.3 建议质量分与纪律执行分分开

建议质量分回答：

```text
AI 和系统当时给的判断，对不对？
```

纪律执行分回答：

```text
使用者有没有按系统建议和止损纪律执行？
```

两者不能混在一起。

举例：

- 系统提示 `critical_exit`，后续确实继续下跌，但用户没卖：建议质量高，纪律执行低。
- 系统提示 `add_allowed`，后续跌破止损，但用户按止损离场：建议质量低，纪律执行高。
- 系统提示 `data_insufficient`，用户没有操作：建议质量不评分，纪律执行正常。

### 9. P4 持仓动作记录

P4 需要补“人实际做了什么”，否则只能评价建议，不能评价纪律执行。

建议新增：

```text
portfolio_action_log
```

核心字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `position_id` | 持仓 ID |
| `code` | 股票代码 |
| `action_type` | `buy` / `sell` / `add` / `reduce` / `manual_note` / `strategy_change` |
| `action_time` | 动作时间 |
| `price` | 动作价格 |
| `quantity` | 动作数量 |
| `reason` | 用户记录原因 |
| `related_advice_run_id` | 关联 AI 建议，可为空 |
| `created_at` | 创建时间 |

V1 不需要接券商接口，先做手动记录：

- 持仓新增时自动生成一条 `buy`。
- 修改成本 / 数量 / 策略时生成 `strategy_change` 或 `manual_note`。
- 用户可以手动记录减仓、加仓、清仓。
- 后续再考虑导入券商成交单。

### 10. P5 页面形态

持仓页面继续保持“摘要优先”，不要变成一屏长报告。

建议页面分三层：

1. 持仓列表：看风险等级、浮盈亏、建议摘要、纪律提醒、是否需要刷新。
2. 详情弹窗：看完整 AI 建议、支撑压力、操作计划、数据快照。
3. 复盘历史：看这只票历次建议、用户动作和后续表现。

新增复盘视图建议：

- 按股票查看建议链路。
- 按建议等级统计命中率。
- 按策略类型统计表现。
- 单独展示纪律违反次数。
- 单独展示 AI 建议与本地硬规则冲突次数。

### 11. 当前下一步优先级

最高优先级改为：

```text
P3 复盘闭环
+ portfolio_advice_outcome
+ 建议后 1/3/5/20 日表现
+ 建议质量分
+ 纪律执行分
```

建议执行顺序：

1. 新增 `portfolio_advice_outcome` 表和 schema 初始化。
2. 写一个后台脚本，扫描已完成且未评价的 `portfolio_advice_run`。
3. 用 K 线和实时快照计算 1 / 3 / 5 / 20 日结果。
4. 在 `/api/portfolio` 详情里返回最近建议的评价摘要。
5. 页面详情弹窗增加“建议复盘”区域。
6. 再补 `portfolio_action_log`，开始区分建议质量和纪律执行。

完成 P3 后，系统才算真正从“能约束交易纪律”进入“能复盘纪律和建议质量”的阶段。

## 项目概览

**项目周期**: 14周（约3.5个月）
**目标**: 构建可扩展、可回测、可视化的股票分析平台

---

## 阶段划分

### 阶段P0: 数据回测系统（Week 1-3）
**目标**: 验证策略有效性，避免实盘亏损

**Week 1: 回测框架搭建**
- [ ] 设计回测引擎架构
- [ ] 实现历史数据加载器（Baostock/AkShare）
- [ ] 实现模拟交易账户（虚拟资金、持仓）
- [ ] 实现绩效计算（收益率、夏普比率、最大回撤）

**Week 2: 策略接入**
- [ ] 将V9选股器改造为可回测格式
- [ ] 实现每日选股 → 模拟买入 → 次日卖出流程
- [ ] 添加滑点、手续费模拟
- [ ] 支持多策略并行回测

**Week 3: 报告生成**
- [ ] 回测报告可视化（收益曲线、交易记录）
- [ ] 策略对比（V9 vs 简单买入持有）
- [ ] 参数敏感性分析（不同阈值的效果）

**交付物**:
```bash
python3 backtest.py --strategy v9 --start 20240101 --end 20241231 --initial 1000000
# 输出: 回测报告 + 收益曲线图
```

---

### 阶段P1: 数据源插件化（Week 4-5）
**目标**: 统一数据源接口，支持动态切换

**Week 4: 插件框架**
- [ ] 设计 `DataSourcePlugin` 抽象基类
- [ ] 实现插件加载器（自动发现插件）
- [ ] 实现数据源管理器（优先级、故障转移）
- [ ] 迁移现有数据源（东财、腾讯、新浪）

**Week 5: 高级功能**
- [ ] 数据源健康检查（自动检测可用性）
- [ ] 多源数据融合（加权平均、投票机制）
- [ ] 数据质量监控（异常值检测）
- [ ] 配置热更新（不停机切换数据源）

**交付物**:
```python
# 自动选择最优数据源
data_source = DataSourceManager()
data_source.register("eastmoney", EastmoneyPlugin(priority=1))
data_source.register("tencent", TencentPlugin(priority=2))
stocks = data_source.get_spot()  # 自动故障转移
```

---

### 阶段P2: 多版本策略并行（Week 6-7）
**目标**: 支持A/B测试，逐步优化策略

**Week 6: 策略插件化**
- [ ] 设计 `StrategyPlugin` 抽象基类
- [ ] 策略版本管理（V9、V9.1、V10等）
- [ ] 策略配置化（JSON/YAML定义参数）
- [ ] 并行运行框架（同一股票多策略评分）

**Week 7: 策略管理**
- [ ] 策略权重配置（V9占70%，V10占30%）
- [ ] 实时效果监控（各策略胜率对比）
- [ ] 自动调参（网格搜索最优参数）
- [ ] 策略回滚（新版本表现差自动回退）

**交付物**:
```yaml
# strategies.yaml
strategies:
  - name: v9_conservative
    class: V9Screener
    params:
      threshold: 65
      position_ratio: 0.8
    weight: 0.6
    
  - name: v10_aggressive
    class: V10Screener
    params:
      threshold: 55
      position_ratio: 1.0
    weight: 0.4
```

### 阶段P3: 事件驱动架构（Week 8-10）
**目标**: 解耦模块，支持异步处理

**Week 8: 事件总线**
- [ ] 实现本地事件总线（基于Redis或内存）
- [ ] 定义标准事件格式（data.fetched, stocks.selected等）
- [ ] 事件持久化（防止丢失）

**Week 9: 服务拆分**
- [ ] 数据采集服务（独立进程）
- [ ] 选股策略服务（独立进程）
- [ ] 报告生成服务（独立进程）
- [ ] 通知推送服务（独立进程）

**Week 10: 消息队列**
- [ ] 引入 Redis/RabbitMQ
- [ ] 实现任务队列（回测任务排队）
- [ ] 实现延迟任务（定时选股）
- [ ] 监控和告警

**交付物**:
```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│ DataService  │────▶│ EventBus     │────▶│ ScreenService│
└──────────────┘     └──────────────┘     └──────────────┘
                            │
                            ▼
                     ┌──────────────┐
                     │ ReportService│
                     └──────────────┘
```

### 阶段P4: Web管理界面（Week 11-14）
**目标**: 可视化配置和监控

**Week 11-12: 后端API**
- [ ] RESTful API设计（FastAPI/Flask）
- [ ] 数据源管理API（增删改查）
- [ ] 策略管理API（启停、调参）

**Week 13-14: 前端界面**
- [ ] 数据源状态面板（健康度、延迟）
- [ ] 策略配置界面（表单调参）
- [ ] 回测结果展示（图表、对比）
- [ ] 实时监控（今日选股、持仓盈亏）

**交付物**:
```

├── 仪表盘（今日市场、选股结果）
```
