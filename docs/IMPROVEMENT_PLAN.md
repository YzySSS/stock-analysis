## 2026-06-12 架构更新：纪律型私人投研工作台

> 本节为当前最新产品与架构边界，优先级高于早期“14 周完整平台化”设想。
> 当前项目不走自动交易系统，也不急于拆微服务；先建设“能约束交易纪律、能解释、能复盘”的个人投研工作台。

### 1. 最新产品定位

当前阶段定位为：

```text
个人纪律型投研工作台
```

核心目标：

- 现阶段只给个人使用，后续可能开源给其他人自部署。
- 产品形态是私人投研工具，不是券商交易终端，也不是自动交易机器人。
- 输出用于辅助分析，重点帮助使用者遵守交易纪律、减少个人情绪影响。
- 系统不自动下单，不接券商自动交易；边界停留在“建议、提醒、复盘、纪律约束”。
- 后续开源时仍沿用当前模型和数据源体系，但使用者必须配置自己的 API key / 数据源 key。

### 2. 推荐架构风格

采用：

```text
模块化单体 + 异步任务驱动 + 可追溯 AI 决策层
```

暂不拆微服务。

原因：

- 当前主要是个人使用，部署和排障简单性优先。
- 后续开源时，模块化单体更容易安装、理解和二次开发。
- 页面响应速度、数据准确性、建议可解释性优先于服务拆分。
- DeepSeek / AI 分析允许后台异步执行，不应阻塞核心页面加载。
- AI 可以作为决策者，但必须被真实行情、技术指标、筹码、资金流、持仓策略和纪律规则约束。

### 3. 核心领域边界

#### 3.1 数据层：回答“事实是什么”

负责采集、同步和质量标记：

- 行情 K 线
- 盘中接近实时价格
- ETF 行情 fallback
- 资金流
- 筹码分布
- 舆情与新闻质量
- 基本面 / 估值

要求：

- 行情 K 线是当前最可信数据主线。
- 数据缺失时必须显式暴露 `data_insufficient` 或缺失原因。
- 不允许在关键数据缺失时硬编买卖建议。

#### 3.2 指标层：回答“结构是什么”

负责从数据层计算结构化指标：

- MA5 / MA10 / MA20 / MA60
- ATR / 波动率
- 20 日高低点
- 动态支撑位 / 压力位
- 量能确认
- 筹码胜率、筹码中枢、上方压力区
- 资金活跃度与资金方向

要求：

- 支撑位、压力位、止损位、止盈位优先由系统按规则计算。
- AI 可以解释这些位置，但不能脱离数据凭空改数值。

#### 3.3 纪律层：回答“应该遵守什么规则”

持仓策略固定为三类：

| 策略 | 默认持仓周期 | 默认风控倾向 | 重点指标 |
| --- | --- | --- | --- |
| 短期 | 1-5 天 | 最大可接受亏损 3%-5% | 实时价、MA5、MA10、量能、ATR |
| 波段 | 1-4 周 | 最大可接受亏损 6%-10% | MA20、箱体、筹码压力、资金活跃 |
| 长期 | 1-6 个月以上 | 最大可接受亏损 12%-18% | 大级别趋势、估值、基本面、行业逻辑 |

当前约定：

- 最大可接受亏损按策略默认设置。
- 后续可支持单只持仓覆盖，但 V1 先不强迫用户逐票配置。
- 同一持仓的 AI 建议在一定时间内复用，不每次页面加载都重复生成。
- 违反纪律时必须提醒，例如跌破止损、亏损超限、持仓周期超限、追高风险等。

#### 3.4 AI 决策层：回答“综合判断是什么”

AI 可以作为最终建议生成者，但必须基于结构化输入快照。

每次 AI 建议必须保存：

- `position_id`
- `stock_code`
- `strategy_type`
- `holding_cost`
- `quantity`
- `realtime_price`
- `latest_trade_date`
- `technical_indicators`
- `support_levels`
- `resistance_levels`
- `chip_snapshot`
- `moneyflow_snapshot`
- `sentiment_snapshot`
- `discipline_rules`
- `model_name`
- `prompt_version`
- `raw_response`
- `parsed_decision`
- `decision_level`
- `created_at`
- `expires_at`

建议分级：

| 等级 | 含义 |
| --- | --- |
| `critical_exit` | 强制止损 / 严重违反纪律 |
| `reduce` | 减仓 |
| `hold_watch` | 持有观察 |
| `add_allowed` | 允许加仓 |
| `no_action` | 不操作 |
| `data_insufficient` | 数据不足，不给建议 |

#### 3.5 复盘层：回答“建议有没有用、纪律有没有执行”

后续需要记录：

- AI 建议后的真实走势
- 建议是否触发止损 / 止盈 / 加仓
- 使用者是否违反纪律
- AI 建议与系统硬规则是否冲突
- 不同策略周期下的实际表现

目标不是让 AI “永远预测正确”，而是让系统逐步评估：

- 哪类建议可靠
- 哪类数据缺失会误导
- 哪类纪律最能降低情绪化交易

### 6. 当前架构落地状态

截至 2026-06-12，持仓建议链路已经从“页面同步问 AI”改成“后台生成、落库复用、页面读取”的形态：

- `portfolio_position` 记录手动持仓、成本、数量、持仓策略、买入时间和风控覆盖项。
- `portfolio_advice_run` 记录每次 AI 建议的状态、输入快照、模型、prompt 版本、原始输出、解析结果、建议等级和过期时间。
- `/api/portfolio` 只读取持仓事实、本地纪律摘要和最近未过期 AI 建议，不再等待 DeepSeek。
- `POST /api/portfolio/{position_id}/advice/refresh` 触发后台刷新建议。
- 页面进入时先看摘要；完整建议通过详情弹窗查看。
- 数据不足、AI 失败、纪律冲突不会阻塞持仓列表加载，而是作为状态暴露给页面。

当前架构的主线已经切换为：

```text
持仓事实
  -> 数据快照
  -> 系统指标与纪律规则
  -> AI 建议生成
  -> 建议落库
  -> 页面复用
  -> 后续复盘评价
```

### 7. 最新模块边界

#### 7.1 持仓模块

职责：

- 管理手动录入持仓。
- 按单个持仓选择短期、波段、长期策略。
- 计算成本、现价、浮盈亏、持仓天数、策略约束和本地纪律提醒。
- 读取最近一次有效 AI 建议，不主动发起慢请求。

不负责：

- 自动下单。
- 账户资金同步。
- 券商接口接入。
- 替用户决定真实交易。

#### 7.2 AI 建议模块

职责：

- 基于结构化输入快照生成建议。
- 输出建议等级、摘要、完整分析、风险、操作计划、支撑压力和失效条件。
- 保存原始响应与解析结果，方便后续排错和复盘。
- 在模型失败或输出不可解析时明确失败原因。

约束：

- AI 不直接改写系统计算出的成本、现价、止损、压力位等硬数据。
- AI 建议必须带 `prompt_version` 和 `model_name`。
- AI 建议必须有过期时间。
- AI 建议要能被本地纪律规则覆盖或否决。

#### 7.3 纪律规则模块

职责：

- 根据持仓策略定义最大亏损、持仓周期、追高风险和止损约束。
- 在 AI 建议之前先给出本地硬规则判断。
- 在 AI 建议之后检查是否存在冲突。
- 生成可用于页面展示的 `discipline_alerts`。

当前规则优先级：

1. 数据不足时，不给确定性操作建议。
2. 跌破止损或亏损超限时，本地纪律优先级高于 AI 观望建议。
3. 已明显追高时，不允许 AI 直接给出无约束加仓建议。
4. 短期策略对盘中价格更敏感，长期策略对日内波动降噪。

#### 7.4 复盘评价模块

职责：

- 统计 AI 建议发出后的真实走势。
- 判断建议是否命中、失效或反向。
- 区分“建议质量”和“纪律执行”。
- 形成长期可查询的建议历史。

这是下一阶段的主建设方向。

### 8. P3 复盘闭环设计

P3 的目标不是继续让 AI 写更多文字，而是回答：

```text
这条建议后来有没有用？
我有没有遵守纪律？
系统哪里判断错了？
```

#### 8.1 新增建议结果评价表

建议新增：

```text
portfolio_advice_outcome
```

核心字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `advice_run_id` | 对应 `portfolio_advice_run.id` |
| `position_id` | 对应持仓 |
| `code` | 股票代码 |
| `decision_level` | 建议等级快照 |
| `base_price` | 建议生成时参考价格 |
| `evaluate_at` | 评价时间 |
| `horizon_days` | 评价周期，支持 1 / 3 / 5 / 20 |
| `latest_price` | 评价时最新价 |
| `return_pct` | 从建议价格到评价价格的收益 |
| `max_gain_pct` | 建议后最大浮盈 |
| `max_drawdown_pct` | 建议后最大回撤 |
| `stop_loss_touched` | 是否触发止损 |
| `take_profit_touched` | 是否触发止盈 |
| `support_broken` | 是否跌破关键支撑 |
| `resistance_broken` | 是否突破压力 |
| `outcome_label` | `hit` / `miss` / `neutral` / `invalidated` / `data_insufficient` |
| `quality_score` | 建议质量分 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

#### 8.2 评价口径

不同建议等级使用不同评价标准：

| 建议等级 | 正向命中 | 负向失败 |
| --- | --- | --- |
| `critical_exit` | 后续继续下跌、跌破支撑、触发止损 | 后续快速反弹且未跌破纪律线 |
| `reduce` | 后续风险扩大或收益回吐 | 后续继续强势突破 |
| `hold_watch` | 未触发止损，走势符合区间判断 | 跌破止损或出现明显反向 |
| `add_allowed` | 后续上涨或突破压力 | 加仓后快速回撤 |
| `no_action` | 波动不大，未出现明确信号 | 出现本应识别的风险或机会 |
| `data_insufficient` | 后续仍缺数据，不计入质量 | 数据其实足够但系统误判不足 |

注意：

- `data_insufficient` 不应强行算成 AI 预测失败。
- 如果建议生成时关键数据缺失，评价时必须保留缺失原因。
- 同一周期内同时触发止盈和止损时，短期策略按保守口径优先判定风险；长期策略需要结合收盘价与支撑位确认。
- 入选/买入当天不触发止盈或止损卖出；最早从入选后的下一个交易日开始，才允许把价格触达冻结为止盈/止损完成。

#### 8.3 建议质量分与纪律执行分分开

建议质量分回答：

```text
AI 和系统当时给的判断，对不对？
```

纪律执行分回答：

```text
使用者有没有按系统建议和止损纪律执行？
```

两者不能混在一起。

举例：

- 系统提示 `critical_exit`，后续确实继续下跌，但用户没卖：建议质量高，纪律执行低。
- 系统提示 `add_allowed`，后续跌破止损，但用户按止损离场：建议质量低，纪律执行高。
- 系统提示 `data_insufficient`，用户没有操作：建议质量不评分，纪律执行正常。

### 9. P4 持仓动作记录

P4 需要补“人实际做了什么”，否则只能评价建议，不能评价纪律执行。

建议新增：

```text
portfolio_action_log
```

核心字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `position_id` | 持仓 ID |
| `code` | 股票代码 |
| `action_type` | `buy` / `sell` / `add` / `reduce` / `manual_note` / `strategy_change` |
| `action_time` | 动作时间 |
| `price` | 动作价格 |
| `quantity` | 动作数量 |
| `reason` | 用户记录原因 |
| `related_advice_run_id` | 关联 AI 建议，可为空 |
| `created_at` | 创建时间 |

V1 不需要接券商接口，先做手动记录：

- 持仓新增时自动生成一条 `buy`。
- 修改成本 / 数量 / 策略时生成 `strategy_change` 或 `manual_note`。
- 用户可以手动记录减仓、加仓、清仓。
- 后续再考虑导入券商成交单。

### 10. P5 页面形态

持仓页面继续保持“摘要优先”，不要变成一屏长报告。

建议页面分三层：

1. 持仓列表：看风险等级、浮盈亏、建议摘要、纪律提醒、是否需要刷新。
2. 详情弹窗：看完整 AI 建议、支撑压力、操作计划、数据快照。

### 16. 页面响应性能与性能可观测性（第一阶段已完成，持续治理）

架构整改完成后，页面性能进入独立改进项。目标不是靠隐藏数据或长期返回陈旧缓存换取表面速度，而是把列表、汇总和重型明细拆成与页面用途匹配的查询边界，并为关键接口保存可重复的冷/热基线。

第一目标为“跟踪复盘”。2026-07-18 本机串行实测：`/api/tracking/deep-review/status` 约 `2ms`，`/api/tracking/filters` 约 `15ms`；默认 compact 跟踪接口冷请求约 `3.60s`，60 秒汇总缓存命中后约 `65ms`。慢点集中在汇总缓存未命中时：64 条纳入统计记录会重复加载完整 tracking record，并扫描日线区间、全市场 1 分钟 raw 与 tracked 1 分钟数据；两张分钟表对跟踪标的存在大量重叠。

本阶段按以下顺序整改：

1. 跟踪极值只从长期产品层 `daily_kline + stock_realtime_intraday_tracked` 读取，当前实时价继续由 `stock_realtime_snapshot` 补齐；不再重复扫描只保留 2 个交易日的全市场 raw 1m。
2. 区间边界按真实 `selection_result.trade_date` 计算，并使用与索引一致的日期/分钟字段，避免以保存时间代替选股日期及按代码扫描全部历史行。
3. 冻结优化前后的 tracking 响应语义，补 Repository/Route 回归；若查询边界优化后冷请求仍不能稳定达标，再把列表首屏与全局汇总拆成两个可独立完成的请求。
4. 第一阶段验收目标：本机默认 compact 接口缓存命中 `< 150ms`，缓存未命中 `< 800ms`；页面首屏不被 AI 状态或非首屏明细阻塞。后续再为 Dashboard、Selection、Backtest、Portfolio 建立同样的冷/热基线和慢查询预算。

2026-07-18 第一阶段已部署：跟踪区间改为从真实选股交易日后的首个交易日开始，日线范围强制使用 `code + trade_date` 复合索引；分钟极值只读取 tracked 1m，不再与全市场 raw 1m 重复扫描。该修复同时纠正了“入选当天被计为已跟踪 1 天”的旧口径。API 重启后的真实首次请求由约 `3.60s` 降至 `0.242s`，随后四次为 `0.034～0.038s`；176 项回归、编译、readiness、migration 20/20 与三类空队列均通过。第一阶段目标已达到，后续页面按真实慢点逐项治理，不做无基线的泛化重写。
