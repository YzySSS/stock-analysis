# 页面慢请求整改（2026-11-13）

后续从存储规模、数据库往返、连接池、SQL条数和实际扫描量展开的 [查询链路审计](query_chain_audit_2026-11-13.md) 记录了两处额外等价修复及仍需分阶段收敛的读模型债务。

## 真实症状与根因

用户在约15:17切换页面时，线上日志记录策略列表 `3.12～5.35s`、首页指数 `3.04s`；认证本地复现分别 `3.71s / 2.54s`。HTML约4ms，CPU负载低，五服务正常，非静态资源/CDN阻塞，也没有证据支持重启整机或扩容。

1. 策略能力的数据快照查询选错MySQL访问路径：先按股票连接历史表，再过滤日期，覆盖率几条查询分别约 `1.08 / 1.17 / 0.52 / 0.65s`。页面切换还可能同时触发重复缓存未命中。
2. 三指数首次读取需四个串行外部请求；原缓存30秒过期后，页面仍同步等待全部刷新，四次TLS建连进一步放大耗时。腾讯分钟接口现场不支持多个代码合并请求，未采用错误的“批量”方案。

## 修复边界

- `app/api/strategy_display.py` 是仅供策略列表/详情GET使用的只读数据投影，指定**既有**日期索引及日期优先join顺序，60秒缓存及单飞锁；覆盖率、日期、分母、候选快照选择与原能力服务一致，异常不回落过期就绪结果。测试逐条对照两条SQL路径仅访问提示有差异，真实输出除采集时刻外相同。
- 不修改冻结研究实现 `app/shared / app/strategies / app/stock_selection`，不改提交时/Worker的原始能力检查。API投影与原查询有意独立，后续更改字段/过滤口径必须同步对照测试，不能让页面显示与提交门槛漂移。
- 指数仍30秒新鲜、最多保留15分钟，过期但尚保留的真实行情立即返回，唯一后台线程按键串行更新；线程内复用HTTP连接。缺数据的真正冷请求仍同步读取，不伪造走势。失败退避30秒，不延长旧证据寿命。
- UI保留原版面与提供方日期；明确显示“后台更新中”或上游失败缓存状态，更新完成会自动重读并停止短轮询。单个日线切换也会完成刷新，不永久停在“更新中”。
- 无migration、数据库维护、策略参数/调度/默认值变更，仅受控重启API；四Worker、09:25研究和09:35自动选股配置未改。

## 多页面补充复核

用户随后明确“多个页面都慢”，因此本轮不只等主要元素出现：逐页等待全部初始GET响应/二级详情并区分HTML、首次内容绘制与数据完成。服务器侧单Chromium串行测试10页，另做80ms/5Mbps网络模拟；这些仍不是请求者电脑/真实运营商网络实测。

### 追加发现与最小修复

- 公共静态资源已走HTTP/2、gzip及1小时浏览器缓存，跨页相同URL的资源传输大小为0；不存在公共外部CDN依赖阻塞证据。
- 真实无人访问后的首页summary首次网络请求4653ms（包含行情库冷读波动），指数约2205ms；该summary也是选股初始化的第一步，故影响不止首页。上轮缓存命中/主要元素验收未覆盖这一情形。
- cProfile及SQL计时定位到情绪板“最近完整日线交易日”：按股票连接全部历史日线，再过滤日期。旧计划该查询1090ms；仅使用已存在的`idx_trade_date`并以`STRAIGHT_JOIN`固定日期优先，新计划42ms。95%完整性、45天回看、股票/退市过滤及返回字段完全不变，无DDL。
- 同一暖DB条件、不使用summary缓存，完整构建1399ms→431/432ms；108,581字节完整payload三次SHA-256均为`f3bde42a22f8d78a7d9f7c652db52e8e93e1f1b2279d4f9a84a72b6dec89db4a`。不能将最早冷读4653ms和新暖DB431ms宣传为完全同条件收益。
