# V2 模块化架构与回测设计草案（2026-05-04）

## 1. 设计目标

本设计文档用于回答当前 `stock-analysis` 下一阶段的几个核心问题：

1. 现有 V1 功能如何从“能跑的页面 + 脚本集合”升级为“模块化系统”
2. V2 应如何拆分领域模块，避免继续把逻辑堆在 `stock_basic / selection_result / 页面脚本` 周围
3. 如何把回测能力正式纳入主线，而不是继续停留在历史脚本和研究仓遗产里
4. 如何兼顾当前 V1 收口工作与 V2 设计推进，避免重构过早或后续返工

本次设计不是直接开启大重构，而是先给出一份 **V2 结构化蓝图**，作为后续开发与取舍依据。

---

## 2. 当前项目判断

## 2.1 当前所处阶段

当前项目已经不再是“从 0 到 1 搭页面”的阶段，而是进入：

- V1 主链路已基本跑通
- 数据状态语义正在变真实
- 现有模块开始暴露边界
- 回测、历史因子、模块化能力开始成为下一阶段瓶颈

一句话概括：

> 当前项目已经从“把系统做出来”切换到“把系统说真话、支持历史验证、并具备持续演进能力”的阶段。

---

## 2.2 当前 V1 已具备的能力

### 已基本可用

1. **选股中心**
   - 可运行策略
   - 可展示结构化结果
   - 支持阈值与最大入选数
   - 支持 preview 结果与保存

2. **跟踪复盘**
   - 已从 `run_id` 心智切换为 `选股日期 + 策略 + 股票`
   - 支持已保存结果查询与删除

3. **策略管理 / 因子分析**
   - 策略状态已分为 `可执行 / 实验中 / 仅展示`
   - 当前可展示基础因子信息

4. **系统状态页**
   - 已区分 K 线缺口语义
   - 已拆分估值缺口语义
   - PE 缺口已开始拆出 `not applicable`

5. **数据主链路**
   - `daily_kline` 主体已稳定
   - `stock_status_snapshot` 已上线
   - `fundamental_sync` / `valuation_sync` 已可持续跑批

---

## 2.3 当前真正的瓶颈

当前最限制系统继续演进的，不再是缺页面，而是以下结构性问题：

### 问题 A：现有能力尚未模块化
- 页面、接口、数据同步、策略逻辑虽然已能协作
- 但领域边界仍不够清晰
- 继续迭代容易出现“哪里都能改一点，最后没人知道主语义在哪”

### 问题 B：`stock_basic` 承担了过多职责
当前它既承担：
- 股票基础信息
- 当前基本面快照
- 当前估值快照
- 一部分数据质量判断基础

V1 可以接受，但 V2 再继续叠会变成“杂物间表”。

### 问题 C：当前选股是“当前快照驱动”，不是“历史回放驱动”
V1 当前选股能跑，但更多是面向“当前选股”和“当前解释”。

一旦进入：
- 历史回测
- 策略验证
- 按日复盘
- 因子效果分析

就不能继续只吃当前 `stock_basic` 快照。

### 问题 D：回测能力尚未主线化
当前仓库中存在历史研究脚本和思路，但：
- 没有统一回测数据输入协议
- 没有统一回测运行表
- 没有统一回测结果展示页面
- 没有明确与当前策略主线的衔接关系

---

## 3. V2 设计目标

V2 的目标不应理解成“多做几个页面”，而应理解为：

> 把当前研究型系统升级成一个 **模块边界清晰、数据语义真实、支持历史回放与回测验证** 的产品型分析平台。

本阶段建议 V2 聚焦四个目标：

1. **领域模块化**
2. **历史因子输入层正式化**
3. **回测能力主线化**
4. **前台信息架构统一化**

---

## 4. V2 模块化设计

## 4.1 推荐模块划分

建议将现有系统逐步收束为 7 个核心模块：

### 1. 基础资产模块（Universe / Master Data）
负责：
- 股票基础信息
- 市场 / 行业 / ST / 退市状态
- 基础资产池维护

当前主要表：
- `stock_basic`

V2 定位：
- `stock_basic` 只保留“基础主数据 + 当前快照辅助字段”
- 不继续无限叠加历史语义字段

---

### 2. 行情模块（Market Data）
负责：
- 日线行情
- 后续复权因子
- 大盘/指数行情
- 交易日与价格取数规则

当前主要表：
- `daily_kline`

V2 增强方向：
- 增加指数行情上下文
- 引入 `adj_factor_daily`
- 为回测提供统一价格读取协议

---

### 3. 基本面与估值模块（Fundamental & Valuation）
负责：
- 当前快照型基本面 / 估值
- 历史按日映射输入
- 数据缺口与口径不适用语义

当前表：
- `stock_basic`

V2 新主表：
- `factor_input_daily`

这层要解决的核心不是“多几个字段”，而是：
- 哪些字段是当前快照
- 哪些字段是历史某日可见输入
- 哪些字段是严格口径 / fallback 口径

---

### 4. 选股执行模块（Selection Engine）
负责：
- 当前选股运行
- 候选池生成
- 策略分发与执行
- explain 结构统一

当前代码主线：
- `app/stock_selection/selector.py`
- `app/strategies/*`
- `selection_result`

V2 目标：
- 明确“当前选股”和“历史回测选股”是同一套策略接口、不同输入源
- 策略不直接绑定当前快照表

---

### 5. 跟踪复盘模块（Tracking & Review）
负责：
- 已保存入选股票跟踪
- 复盘结果
- 人类可读表现汇总

当前主线：
- tracking 页面
- `selection_result` 持久化记录

V2 目标：
- 与选股运行结果保持稳定关系
- 继续坚持产品主语义是 `策略 + 日期 + 股票`，而不是 `run_id`

---

### 6. 回测模块（Backtest）
负责：
- 历史时间段选股回放
- 1日 / 3日收益计算
- 策略历史表现统计
- 回测页面展示

V2 新主线：
- `backtest_run`
- `backtest_pick`
- `backtest_trade`
- `backtest_summary_daily`

这将是 V2 最重要的新能力之一。

---

### 7. 系统状态与数据可信度模块（System & Data Quality）
负责：
- 覆盖率
- 缺口分层
- 状态快照
- not applicable / source missing / actionable 缺口区分

当前主线：
- `/api/system/status`
- `stock_status_snapshot`

V2 目标：
- 从“监控页”升级成“数据可信度面板”
- 成为整个系统的统一质量语义源

---

## 4.2 推荐代码结构方向

建议 V2 逐步向以下结构演进：

```text
app/
  api/
    routes/
      selection.py
      tracking.py
      backtest.py
      system.py
      strategies.py
      stocks.py

  domain/
    universe/
    market_data/
    fundamentals/
    selection/
    tracking/
    backtest/
    system_status/

  services/
    selection_service.py
    tracking_service.py
    backtest_service.py
    system_status_service.py

  repositories/
    stock_repository.py
    factor_input_repository.py
    selection_result_repository.py
    backtest_repository.py

  strategies/
    active/
    registry/
```

### 设计意图
- `domain/`：放领域模型与规则
- `services/`：放跨模块编排逻辑
- `repositories/`：放 SQL 与数据访问
- `routes/`：只做 API 输入输出，不承载业务主逻辑

这不要求现在一次性重构完成，但应作为后续收敛方向。

---

## 5. 数据层设计方向

## 5.1 `stock_basic` 的 V2 角色

V2 中，`stock_basic` 建议明确为：

> **基础股票主数据 + 当前快照辅助层**

保留：
- `code`
- `name`
- `market`
- `industry`
- `instrument_type`
- `is_st`
- `is_delisted`
- `listing_date`

允许保留一小部分当前快照字段：
- `pe_tushare`
- `pb_tushare`
- `roe`
- `roa`
- `profit_yoy`
- `eps`
- `valuation_updated_at`
- `fundamental_updated_at`

但要明确：
- 它不再承担“历史回放正式输入层”角色
- 历史回测 / 历史因子分析必须逐步迁往 `factor_input_daily`

---

## 5.2 `factor_input_daily` 作为 V2 历史输入核心

建议把 `factor_input_daily` 作为 V2 历史输入主表。

它至少承载：
- 历史日期对应的估值输入
- 历史日期对应的换手 / 成交额 / 市值输入
- 历史日期可见的基本面映射输入
- 数据来源 / 口径 / completeness 信息

它解决的根问题是：

> 策略和回测不再依赖“现在数据库里这一刻看到的快照”，而依赖“那一天本来应该看到的输入”。

---

## 5.3 状态层保持独立快照

`stock_status_snapshot` 已经证明方向正确，建议继续保留并增强。

未来可继续把：
- 停牌
- 暂停上市
- 上游缺口
- 口径不适用
- 风险标签

统一进“状态语义层”，而不是散落到多个接口临时判断。

---

## 6. 回测模块设计

## 6.1 回测目标

V2 回测模块第一阶段只解决最小闭环：

1. 能选一个策略
2. 能指定时间区间
3. 能按历史日期逐日运行
4. 能输出：
   - 一日收益
   - 三日收益
5. 能看每日表现、总收益、胜率、样本数

### 收益口径沿用既有历史逻辑
- **1日收益**：当日开盘买入 → 次日开盘卖出
- **3日收益**：当日开盘买入 → 第三日收盘卖出

---

## 6.2 回测主语义

建议明确：

### `backtest_run`
一次完整回测任务

### `backtest_pick`
某日被选中的股票及其当时评分

### `backtest_trade`
单只股票在指定收益口径下的实际收益结果

### `backtest_summary_daily`
按日期汇总后的回测表现

这样能把：
- 任务配置
- 选股时刻
- 收益落地
- 每日汇总

拆清楚，避免以后都塞进一个大 JSON 字段。

---

## 6.3 回测页面设计建议

建议新增独立页面：

### 页面名称
- `回测中心`

### 页面结构

#### 区块 1：回测配置
- 策略选择
- 起止日期
- 收益口径（1日 / 3日）
- 最大入选数
- 分数阈值
- 是否只看可执行策略

#### 区块 2：回测总览
- 回测区间
- 样本日数
- 总入选次数
- 胜率
- 平均收益
- 累计收益（后续可补）
- 最大回撤（第二阶段可补）

#### 区块 3：按日表现
- 每日选了几只
- 每日平均 1日收益 / 3日收益
- 当日胜率

#### 区块 4：个股明细
- 日期
- 股票
- 策略
- 入选分数
- 买入价
- 卖出价
- 1日收益
- 3日收益
- explain 摘要

### 原则
- 第一阶段优先做“可信 + 可读”
- 不一开始就追求高级量化图表大全

---

## 7. 前台产品架构建议

V2 应开始把页面组织成统一工作台，而不是继续“一个功能一个孤岛页”。

建议主导航收敛为：

1. **选股中心**
2. **跟踪复盘**
3. **回测中心**
4. **策略管理**
5. **系统状态**
6. **股票详情**（作为单票钻取页，不一定进一级导航）

推荐用户主流程：

```text
策略管理 → 选股中心 → 保存目标 → 跟踪复盘 → 回测中心验证策略 → 系统状态看数据可信度
```

这样产品心智是统一的，不再只是工具页拼接。

---

## 8. V1 到 V2 的迁移策略

## 8.1 不建议立刻做的事

当前不建议：
- 一次性大改所有目录结构
- 直接推翻 `selection_result`
- 大规模迁移所有页面
- 先做炫图表再补底层语义

因为当前 V1 仍有收口任务，过早重构会打断现有成果。

---

## 8.2 建议的迁移顺序

### 第一阶段：V1 收口 + V2 设计冻结
当前阶段重点：
- 持续补 `eps`
- 稳定 PE not applicable 语义
- 完成文档设计
- 明确表结构与模块边界

### 第二阶段：历史输入层正式化
重点：
- 正式建设 `factor_input_daily`
- 增加 `daily_basic / adj_factor / moneyflow / cyq_perf` 等输入
- 建立按日期读取策略输入协议

### 第三阶段：回测最小闭环
重点：
- 新增回测表
- 新增回测 API
- 新增回测页面
- 让 `lowvol_reversal` 跑出第一版 1日/3日结果

### 第四阶段：策略模块统一化
重点：
- 让当前选股与历史回测尽量共用策略输入接口
- 逐步考虑 `v13_three_factor`
- 再评估 `v12_legacy` 重新纳入主线的成本

---

## 9. 本轮设计建议结论

### 结论 1
**现在已经该正式思考 V2，但还不该立刻全面切 V2 开发。**

正确节奏是：
- 一边继续收 V1 数据可信度
- 一边冻结 V2 结构设计

### 结论 2
**V2 的核心不是“再多几个功能页”，而是模块边界 + 历史输入层 + 回测主线化。**

### 结论 3
**回测应该作为 V2 核心模块进入主线，而不是继续停留在研究脚本层。**

### 结论 4
**模块化不是为了好看，而是为了避免后续继续在 `stock_basic / selection_result / route 里堆逻辑`。**

---

## 10. 建议的下一步动作

建议按以下顺序推进：

1. 继续盯完当前 `fundamental_sync` / EPS 补数收口
2. 基于本设计文档，再补一份更细的：
   - `V2 implementation roadmap`
   - 明确每一阶段要改哪些表 / API / 页面
3. 优先启动：
   - `factor_input_daily` 正式化
   - `backtest_*` 表与 API 第一版
4. 回测第一版只先支持：
   - `lowvol_reversal`
   - 1日 / 3日收益
   - 可读页面展示

---

## 11. 一句话总结

> V1 现在正在变得可信；V2 的任务，是把这套可信能力正式模块化，并补上历史回放与回测验证这条主线。
