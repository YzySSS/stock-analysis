# 舆情选股修改计划：0.6.0 盘中研究版

日期：2026-09-11。状态：待实施计划，不代表代码已修改或服务器已部署。

参考审查基线：`main@6e30b94d6da662e8ba151324c92757be03d58d53`。实施前须重新核对远端提交和工作区，以实际实施基线对账本计划。

用户场景：使用 0.5.1，上午 11 点左右或下午临买前运行选股，买后经常回撤或止损。主要持有期限尚未确认，不在本计划中据此改变实际持有规则。

## 一、目标与边界

目标：把“热点、关注度、既有强势的筛选”完善为“有真实增量事件、公司确实受益、当前确认有效、没有明显过度兑现的候选筛选”，并以可重放的盘中样本验证。

本次计划：

- 只优化舆情选股及其必要的证据、盘中确认、前瞻评价链路，不恢复其他历史选股策略。
- 保留全部现有页面、历史任务、API 兼容与现有默认选择行为。
- 拟新增 `a_share_sentiment_v06 / 0.6.0`，不原地覆盖 0.5.1 和 0.4.4 的冻结逻辑。
- 新版本先 `prototype → shadow_only`；能研究运行不代表具备正式交易资格。后续 `candidate/enabled` 仅由人工审批，不自动晋级。
- AI 继续只做有证据的解释、实体消歧、去重建议和风险摘要，不直接修改正式分数、排序或等级；核心路径不依赖 AI 成功。
- 不下自动订单，不用“选中、保存、计划触发”冒充真实成交。
- 本地只改代码、测试、迁移和文档，不安装 Redis、生产数据库或服务，不连接修改云端。云部署和数据任务另行授权。
- 不将 Portfolio 全面重写、其他页面性能工程纳入本次主任务；会影响新版本评价正确性的成交模型和事件记录列为必要前置项。

不承诺收益提升或更低止损率。工程正确性与策略有效性分别验收。

## 三、逐项修改内容

### W0：锁定基线与版本，隔离算法变更和工程修复

1. 实施前核对最新 main、部署方已用版本和原工作区修改，固定实施 SHA。
2. 为 0.4.4、0.5.1 保存脱敏固定输入及其原输出，覆盖双轨、观察、空结果和风险状态。
3. 新增 0.6.0 注册与独立配置，旧版本使用原适配器；不能通过共享辅助函数修改悄悄改变旧版本结果。
4. 每次结果记录策略版本、配置哈希、特征/因子版本、证据规则版本、输入快照 ID、执行规则版本、评估方法版本与代码 SHA。
5. 将数据契约修复和算法变化分批交付、分组归因。历史评价如需纠错，新增修订版本及原因，不覆盖原记录。
6. 排除污染的 0.5.0 样本；不能拿同名但不同 AI 模式/查询路径的旧结果混合作基线。

主要涉及：`app/strategies/registry/`、`app/strategies/service.py`、`app/stock_selection/sentiment_snapshot.py`、相关策略测试。

验收：旧输入的旧版本输出一致（数值容差不超过 1e-6）；历史任务仍可查询；新版本仅按显式 ID 运行；相同输入、规则与配置可确定性重放。

### W1：重建“事件”这一层，不再把文章数量等同于催化强度

新闻划分为：

- 原始增量催化：订单、业绩变化、明确政策落地、产品/技术实质进展等。
- 催化进展：同一事件新增可验证事实，形成事件新版本。
- 行情描述：涨停、拉升、资金流入、异动复述等，只用于市场反应证据。
- 观点/转载：保留观点和来源关系，不能独立制造业务催化。
- 风险事件：处罚、造假、重大减持、业绩风险等；不因热点更换而丢失。

拟统一事件/证据合同：

| 字段组 | 必需信息 |
|---|---|
| 身份与版本 | canonical_event_id、event_revision、evidence_id、原始新闻 ID |
| 类型与增量 | event_type、content_role、direction、delta_from_previous、confirmation_status |
| 来源 | 原始发布者、采集渠道、转载关系、信誉评级版本、原文引用 |
| 时点 | published_at、first_seen_at、source_time、received_at、available_at、effective_until |
| 驱动力 | 兑现周期、后续节点、是否一次性、是否终结、事实覆盖状态 |

具体动作：

1. 复用已有新闻采集、实体消歧和类型化衰减，不重建抓取器。
2. 把事件归一化放在 `app/` 服务内，现有脚本只作命令入口，禁止 `app/` 反向依赖脚本。
3. 修复 source_id/raw_id 到正式信誉、证据 ID 的映射，硬门与展示使用同一证据解释。
4. 增加跨来源、改标题转载的事件级归并；保留所有原文与归并理由。规则无法确定时标记待确认，AI 不可凭猜测改变正式事件归属。
5. 同一原始事件重复采集不增加事件数量或业务受益分；真正独立的确认可有界提高置信度，不冒充新的催化。
6. 可信度只说明信息可靠；缺少预期基准时，“超预期”必须未知，不能以新闻正面代替超预期。
7. 为持续性字段建立真实生产者，不再回退为新闻时效。信息有效期与后续驱动力分别保存。

主要涉及：`app/data_ingestion/market_opinion_semantics.py`、`market_opinion_storage.py`、`market_opinion_repository.py`、`scripts/run_market_opinion_update.py`、`app/shared/sentiment_scoring.py`。

拟新增事件、事件修订、事件证据、股票关系等最小必要存储；实施时先核对现有表可复用部分，再追加 migration，不预先假定必须新建所有表。

验收：十篇同源转载不变成十个催化；纯行情快讯不能单独进入直接催化轨；新披露事实产生新事件版本；信誉缺失、未知来源和真实零分不会被当作默认合格。

### W2：真正实现分轨召回，保留公司与事件的多重关系

直接催化轨：由通过事件、实体和受益关系检查的公司召回，保留事件规模、确认程度及后续节点。

主题龙头轨：行业/主题映射只负责扩大候选，再用当前同批次的相对强弱、主题参与广度、资金和承接筛选；昨日结构作为背景，不作为唯一的前排认定。

具体动作：

1. 为每只股票保留多条事件和主题关系，不再按 `板块分×72%+股票分×28%` 提前只留一个上下文。
2. 两轨分别召回和打标，之后合并同一股票；不强制各选一只。
3. 业务关系需有可引用的产品、业务、客户、供应链或公告事实；非空说明文字不再等价于关系确认。
4. 能获取可靠规模时，使用决策前已披露的业务数据作尺度；缺失则标明置信度不足。不恢复全市场基本面宽表查询。
5. 保留已有主题/行业限额，对多主题股票增加共同风险标签，避免不同名称绕过实际集中度限制。
6. 候选池限额、截断位置与淘汰原因写入诊断；比较召回覆盖，不能通过过窄候选池遗漏新出现的前排。

主要涉及：`app/stock_selection/selector.py`、`repository.py`、舆情物化器及现有主题层级/市场领导状态模块。

验收：泛主题不能覆盖直接订单证据；负面证据跨轨保留；行业相近但无受益证据的股票只能观察；昨日不强但当前合格的股票可以通过实时召回进入待评池。

### W3：修正评分含义，再研究权重和统一尺度

| 模块 | 下一版应表达的内容 | 应移除或隔离的内容 |
|---|---|---|
| 催化质量 | 该公司事件的增量、重要程度、确认程度 | 上涨报道、股票涨幅、板块均值替代公司事件 |
| 持续性 | 后续驱动力、兑现节点、失效条件 | 用新闻新鲜度代替持续性 |
| 关系/受益强度 | 公司与事件的关系、受益归属与尺度 | 池内排名、涨幅、成交额冒充业务关联 |
| 资金确认 | 同时点的个股与主题资金、强度及持续性 | 缺失当零、合法零值变中性、分子分母混时钟 |
| 价量确认 | 当前相对强弱、承接、量价效率、反应程度 | 多处重复奖励同一涨幅 |
| 筹码与容量 | 可成交容量、流动性、筹码风险 | 单靠成交额大就推导未来收益高 |

具体动作：

1. 每项因子有定义、输入、有效期、缺失行为与方法版本；保留分数贡献和来源。
2. 将动量信息集中到明确的行情模块，检验事件/关系分对纯价格变化保持不变。
3. 直接轨的新闻累加改为有界事件聚合；两轨分别检查分布和样本外分组表现，不能仅因数值都在 0—100 就认为可比。
4. 修复板块资金嵌套字段映射；显式区分 None、0、负值，避免 `or 50` 之类回退改变合法含义。
5. 将数据置信度与机会分数分开，必需数据缺失不得靠中性分获得交易资格。
6. 研究初期保留原六模块外层权重作为一个控制组，不称其最优；先测语义修复，再单独研究权重。新旧同名因子通过 schema/version 区分，不混算。
7. 统一排名先仅用于影子研究；正式采用共同阈值前，须证明两轨分数在同一收益/风险口径下可比较。不得把 68 分解释为 68% 上涨概率。

建议实现：独立的 0.6.0 策略入口与小型纯计算组件，避免继续向冻结混合文件添加大量分支；复用现有 BaseSelectionStrategy、加载器与评价框架。

验收：固定事件证据只提高昨日涨幅，事件与业务关系分不变；重复报道不提高持续性；增加真实增量进展可改变相应因子且可解释；资金合法零值、负值与未知分别测试。

### W4：为盘中运行增加不可被总分抵消的必要确认

将“候选分数”与“当前入场条件”分开。新版本的必要确认包括：

1. 输入时点、批次、覆盖与有效期合格。
2. 对应轨道的事件/业务关系证据合格。
3. 当前市场风险状态不阻止新增风险；复用现有盘中数据，但不静默改变旧版本非阻断提示的含义。
4. 资金与价格承接达到预登记的最低确认条件。
5. 成交状态与容量允许；高总分不能解除停牌、不可成交等限制。

重点补充：事件前价格基准、事件后累计反应、距日高回撤、相对 VWAP/结构位置、分时量价效率、个股相对主题/指数强弱、主题广度及资金变化。

工程约束：

- 同时满足来源时间和接收时间不晚于决策截止；事后补到的旧时间戳数据不能进入过去决策。
- 只用当时完成且已收到的分钟 bar；盘中不使用当天最终日线或全日资金。
- 盘中累计成交与资金需按同一时段、相同单位比较；没有短窗口数据时不得伪称“最近资金持续流入”。
- 行情 TTL、窗口长度、追价距离等配置在影子实验前冻结；具体阈值依据数据可用性和开发样本确定，不在本计划中声称某个阈值最优。
- 区分持续承接、冲高回落、放量滞涨、主题转弱与修复；先生成可审计特征，验证后才作为正式门控依据。
- 必要确认失败时，无论总分多高只能观察/失效；置信度不足同样不能靠其他高分补齐。

已有“90/90/90/30/40/60 总分 68”反例转为回归：构造资金或价量必要门明确失败的输入，不能再凭总分取得合格资格。门的阈值另行版本化，不机械假定不同版本的 30/40 分含义不变。

架构：特征采集、补全与物化通过持久 worker；选股读取一个一致快照后本地计算。GET 不同步抓源、调用 AI 或写库；分钟数据不足先观察，并由独立异步任务补齐。

### W5：保留页面，明确区分分数、条件和验证状态

不删页面，不用新页面替代旧工作流。Selection、个股详情与 Tracking 增量展示：

- 选股轨道与主要事件、所有相关主题及核心业务证据。
- 因子贡献、缺失字段、置信度与门控理由。
- 运行时间、实际决策截止、行情来源时间、快照发布时间与有效期。
- “观察/条件满足/失效”的状态与触发原因。
- 策略和交易规则版本、影子/未验证标签。

拟增量字段：`factor_schema_version`、`evidence_quality`、`candidate_lanes`、`entry_eligibility`、`entry_block_reasons`、`decision_as_of`、`valid_until`、`evaluation_method_version`。最终字段名在实施时与现有 API schema 对账，旧客户端字段不删除。

影子版本即使条件满足也只展示“研究候选”，不暗示正式买入建议；验证状态与条件等级分开。旧版本原始结果与历史页面语义保留。

验收：所有现有路由/API 兼容；AI 失败、分钟线缺失、无合格候选、过期快照和影子状态均能清楚展示；不以保存成功表示买入成功。

### W6：建立与实际使用匹配的前瞻评价

#### 6.1 协议与分组

- 拟新增上海时区 11:00、13:30、14:30 固定决策分组，另保留真实手动运行样本；不将三组或手动样本直接混为同一独立样本池。
- 研究初稿以 3 个交易日净超额收益为主指标，1/5 日为辅助观察；这是研究期限而非建议持有期限。正式收集前冻结主指标，如需修改必须在看锁定测试结果前确定或新开协议。
- 同时报告 MAE/MFE、首次止损、平均盈利/亏损、尾部亏损、候选覆盖、空结果率、合格率、成交率和集中度。
- 0.5.1 与 0.6.0 使用同一决策截止、原始快照、股票范围与公平的执行假设；旧算法由兼容适配器重放，数据修复影响单列。

#### 6.2 拆分改善来源

| 对照 | 固定什么 | 检验什么 |
|---|---|---|
| 召回对照 | 决策时点、原始输入、后续评价规则 | 是否找到此前漏掉的有效候选 |
| 评分对照 | 公共候选池、成交与退出规则 | 新因子含义是否提供额外区分能力 |
| 门控对照 | 候选、排序、执行与成本 | 过滤是否改善净期望和尾部风险，而非只减少样本 |
| 端到端对照 | 原始输入、风险预算、执行/退出方法 | 整体结果是否改善，代价是什么 |

完整保留基础股票池、召回、淘汰、可评分池、完整排名、观察级、最终展示与空运行。全市场快照用批次引用复用，不为每个策略复制全市场历史表；阶段决策与特征按方法持久化。

不能只用 Top 3 或实际买过的股票做横截面因子评估。收益预测、筛选效果和用户实际执行效果分别报告。

#### 6.3 必要的评价正确性前置修复

- 新评估使用可执行时点之后的价格、预登记延迟/滑点与费用，不取决策前的开盘价或入选价冒充成交。
- 实现 T+1 可卖批次、跳空、停牌、涨跌停阻塞、未成交与持仓延续；不得出现高于当天最高价的模拟卖出。
- 复用交易事件账本，首次终态不可随更晚行情改写。旧 Tracking 的全观察期高低点汇总不能作为新版本的正式交易绩效来源。
- 选股版本和交易规则版本独立绑定；新旧选股对照用同一修正后的执行规则，并与旧展示成绩分开标识。
- 原始信号后固定期限收益、模拟交易收益、真实成交收益三种口径分别保存。

#### 6.4 样本外与晋级约束

- 时间顺序划分开发、校准、锁定测试区间；跨界重叠标签剔除，隔离期依据最长持有/评价窗口设定。
- 同股、同日多次运行和重叠持有期不能当作独立样本，按日期/事件分组做配对比较及区块重采样。
- 每次只改一个主要机制，记录全部变体；看测试结果后修改规则必须新开版本或新测试区间。
- 复用现有因子评价协议的样本数、成熟度及多重检验控制；权重不自动学习上线。
- 沿用此前审慎上线原则：至少 20 个交易日用于工程稳定性；30 日可作初步方向观察；120 日形成中期报告；252 日形成完整周期报告后仍需人工审批。数据不足、多市场状态覆盖不足或风险约束失败，不因日数到了而晋级。
- 工程测试、单次收益、止损率下降不能单独作为升级依据。正式晋级前需冻结最低有效样本数、主指标判据和尾部风险限制；若未完成预登记，继续 shadow，不临时降低标准。

### W7：本地交付、云端启用与回滚

本地交付：

1. 代码与版本化配置、追加 migration、数据合同说明、回归测试和离线样例。
2. API/前端兼容检查；Python 编译与相关 unittest，改动 JS 执行 `node --check`。
3. Redis 关闭、异常和 fakeredis 测试；外部行情/新闻/AI 不可用时的降级用例，不安装真实 Redis。
4. 迁移计划可审查；空库与旧结构增量迁移必须在明确授权的隔离 MySQL 测试环境实跑。无测试库时明确列为未验证，不冒称通过。
5. 云端任务清单、环境模板、只读检查命令与回滚步骤；不在文档记录真实密码、Token 或持仓。

云端后续授权执行：

1. 备份并确认恢复方式，核对代码 SHA、现有服务及数据源能力。
2. 先保持现有默认策略与 Redis 配置，检查并应用追加迁移。
3. 物化新事件/关联/盘中特征；只发布完整新批次，不完整不能覆盖上一个可用批次。
4. 验证来源时间、接收时间、覆盖率、选股 worker 终态和新结果展示。
5. 开启新版本配对影子运行，不切换默认正式策略。
6. 在目标 2C4G 环境测量额外 CPU、内存、DB 连接和任务等待；不把全市场新闻/分钟重算塞进选股 API。

性能边界：继续 MySQL 事实源、可选缓存与持久队列；只有物化后才能快速读取。选股提交 p95<200ms、本地确定性选股 p95<10s 等沿用原云端目标，属于待测目标，不是本次计划或本地测试已经达到的结论。

回滚：关闭新版本入口/影子调度，恢复原版本及原查询配置；新表和证据保留，不删除历史或回滚已应用 migration。若共享数据合同影响旧版本，必须由兼容适配器或独立命名空间隔离；不能为回滚覆盖旧数据。

## 四、必过回归用例清单

| 编号 | 场景 | 预期 |
|---|---|---|
| T01 | 同一原始事件重复采集、换标题转载 | 不新增独立催化，不无限累加得分 |
| T02 | 原始订单与“股价拉升”报道 | 前者按证据判断；后者不能单独取得直接催化资格 |
| T03 | 同股同时有直接订单、热门泛主题、负面事件 | 多关系保留，负面不被主题替换隐藏 |
| T04 | 固定事件，只提高昨日涨幅 | 催化与业务关系分不变，只允许行情模块变化 |
| T05 | 刚发布但一次性的消息与有后续节点的事件 | 时效可相同，持续性依据不同，不机械复制时效 |
| T06 | None、0、负资金值 | 分别为未知、零值、负向，不互相替代 |
| T07 | 总分 90，但必要确认失败 | 不能升级合格/交易级；明确返回原因 |
| T08 | 同当前涨幅的持续承接与冲高回落路径 | 根据路径证据区分；同时有合格正例，不能全部拒绝 |
| T09 | 11 点后才收到、但标注 10 点发布的新闻 | 不得进入 11 点历史决策 |
| T10 | 盘中缺分钟线/陈旧快照/不同批次 | 观察或拒绝，不伪造新鲜确认 |
| T11 | 昨日未涨但当前同主题前排且证据完整 | 可被实时召回，不被昨日涨幅入口永久排除 |
| T12 | 买入当天、次日跳空、跌停无法退出 | 正确记录可卖约束、可达价格与阻塞，不虚构成交 |
| T13 | 首次完成后继续上涨或下跌 | 原终态和已完成收益不被重写 |
| T14 | 无候选、数据失败、未触发或未成交 | 全部入统计分母并区分原因，不挑成功样本 |
| T15 | 旧输入运行旧版本；重复运行新版本 | 旧结果保持一致，新结果确定性且事件幂等 |
| T16 | 全部现有页面与旧 API 客户端 | 路由保留、字段兼容、影子标签明确 |

以上是待实施测试，不是已通过清单。
